# Phase 4 — The Acceptance Loop

**Depends on:** Phase 3 · **Est:** ~2.5 weeks · **Critical path:** yes

## Goal

The heart of the product works end-to-end: a Master takes an available stage into work, does it, uploads the mandatory concealed-works photos, and presses Complete (blocked without photos). The Inspector receives the request, opens the digital checklist, walks the control points, and either Rejects (with comment + defect photo, returning the stage to the Master unpaid) or Accepts. On Accept the stage closes. By the end, a single property can be driven from its first stage through acceptance entirely through the two field-role PWAs — though the *consequences* of Accept (wage credit, unlock, notify) are wired in Phase 5.

## Why now

This is the loop the whole TZ is built around (Modules 2 & 3, business-process steps 3 & 4). It needs a property with instantiated stages and checklists (Phase 3) to operate on, and it produces the Accept event that Phase 5's automation hangs off. Everything before this was scaffolding to make this loop possible; everything after either reacts to it (5, 7, 8) or feeds it (6).

## Scope

### 4.0 Sub-stage 1.1 (Initial Property Acceptance) — the first run through this loop
- Before any master works, the **Inspector** runs Sub-stage 1.1 through this very loop: uploads the mandatory "before" media (meter readings, panoramas, door/window condition, risers — TZ 1.1), works the 7-item checklist, and accepts. There is no Master step for 1.1 — the Inspector both performs and accepts it (it's the documentation gate, not a quality handover).
- On 1.1 acceptance, the property → `READY_FOR_PRODUCTION` and the first master stage unlocks (gate logic owned by Phase 3 §3.5; **enforced here** as a normal predecessor dependency — see 4.6).

### 4.1 Master: take into work
- Master PWA shows only available stages matching their specialization on properties they're assigned to (TZ: "sees only their task, the rest hidden").
- "Take into Work" button → stage `AVAILABLE → IN_PROGRESS`, claimed by that master.

### 4.2 Master: media upload (the hard blocker)
- The Master completion form lists the stage's required media (from the snapshotted media requirements, Phase 3/2). Photo is mandatory; video is an accepted optional attachment per **A6** (the field UI accepts both; only photo gates the button unless the tenant marked video required).
- Direct client→R2 upload via presigned `PUT` URLs generated by Elysia using **`Bun.s3`** (Bun's native S3-compatible client — no AWS SDK) — binary never touches the app server. Reuses the pattern proven on floor plans in Phase 3.
- PWA camera capture: take photo (or video) directly in-app (D3 / TZ §4 "take a photo directly in the app").
- **The Complete button is inactive until the required photos are attached** (TZ Module 3, repeated emphasis). Enforced both client-side (button state) and server-side (the submit endpoint rejects without required media, and verifies the objects actually landed in R2).

### 4.3 Master: request acceptance
- Complete → stage `IN_PROGRESS → SUBMITTED`. An acceptance request now exists for the Inspector.

### 4.4 Inspector: acceptance queue & checklist
- Inspector PWA shows a queue of submitted stages awaiting acceptance.
- Opening one shows the digital checklist: every control point as a Yes/No checkbox (with its criteria text where present), plus the master's uploaded media for review.
- Large-button, touch-first layout (D3) — the Inspector is on-site on a phone.

### 4.5 Inspector: resolution (accept / reject)
- **Reject**: comment (required) + defect photo (R2 upload) → stage `SUBMITTED → REJECTED → IN_PROGRESS`, returned to the same master, unpaid. The rejection is recorded (feeds Phase 6 ratings).
- **Accept**: only allowed once checklist resolution is recorded → stage `SUBMITTED → ACCEPTED`, stage closed. **This Accept event is the trigger Phase 5 consumes** — in this phase it simply closes the stage and (synchronously, as a placeholder) unlocks the next stage so the loop is demonstrable; Phase 5 moves the unlock + side effects into reliable async jobs.

### 4.6 Enforce the blocking rule at runtime + Inspector manual override
- The stored rule from Phase 2 / instance state from Phase 3 is now enforced: the API physically refuses to set a stage `AVAILABLE` or accept a master onto it until its predecessor is `ACCEPTED` (TZ Module 2 "physically prevent"). This is a server-side invariant, not just UI. The first master stage's predecessor is Sub-stage 1.1, so this same invariant implements the Ready-for-Production gate.
- **Inspector manual block/unblock (TZ §2, closes finding gap)**: distinct from the automatic flow, the Inspector gets an explicit control to **block** a stage that would otherwise be available (e.g. halting work on a property for a discovered issue) and to **unblock** when resolved. This writes the manual-override flag modeled in Phase 2 §2.3. A manual block overrides automatic availability; a manual unblock does **not** bypass the predecessor-accepted invariant unless the Inspector explicitly force-unblocks (audited). UI lives in the Inspector PWA; the rule is enforced server-side alongside the automatic invariant.

## Out of scope
- Reliable async side-effects of Accept — wage credit, robust unlock, notifications (Phase 5 moves these into BullMQ). Phase 4 may do a *synchronous placeholder* unlock to demonstrate the loop, clearly marked for replacement.
- Master rating math (Phase 6).
- Real-time push of "stage ready" to the Inspector (Phase 8 — for now the queue refetches, per A5).
- Financial dashboard updates (Phase 7).

## Data model touched
- **Per-tenant**: `stage_assignments` (master↔stage), `acceptance_requests`, `checklist_results` (the Yes/No outcomes), `rejections` (comment + defect photo + timestamp), media-asset references for stage photos/video, and the manual block/unblock override records (with audit fields) on stage dependencies.
- `packages/validators`: completion, checklist-result, rejection, manual-override schemas.

## Key risks & decisions
- **Server-side photo enforcement**: the blocker must hold at the API, not just the button. A master must not be able to submit without required media by calling the endpoint directly.
- **Presigned-URL upload integrity**: the server issues presigned URLs via `Bun.s3` but must then confirm the uploads actually landed in R2 before allowing Complete — a presigned URL handed out isn't proof of upload. Verify object existence on submit using `Bun.s3.file(key).exists()` (or equivalent `HEAD` check).
- **Accept is the system's pivotal event.** Even though Phase 5 owns the async fan-out, design the Accept endpoint now to *emit* a clean domain event (rather than inlining logic) so Phase 5 subscribes without rewriting Phase 4.
- **State machine integrity under concurrency**: two actors (master, inspector) act on the same stage. Guard transitions so a stage can't be accepted and re-submitted in a race. Lean on Postgres row-level constraints (the stack doc cites stage-locking as a reason for relational integrity).

## Definition of Done
- [ ] Master takes an available stage, uploads required photos (camera-in-PWA), and the Complete button is dead until photos exist — enforced server-side too.
- [ ] Submitting creates an acceptance request visible in the Inspector's queue.
- [ ] Inspector walks the checklist, sees the media, and can Reject (comment + defect photo → back to master, unpaid) or Accept (stage closes).
- [ ] **Sub-stage 1.1 runs through this loop (Inspector-performed): accepting it moves the property to `READY_FOR_PRODUCTION` and unlocks the first master stage — and the first master stage is unreachable until then.**
- [ ] The blocking rule is enforced at the API: a locked stage cannot be taken until its predecessor is accepted.
- [ ] **The Inspector can manually block an available stage and unblock it, server-side enforced and audited, distinct from the automatic flow.**
- [ ] One property can be driven from 1.1 through at least two consecutive master stages purely through the Master and Inspector PWAs.
- [ ] The Accept endpoint emits a clean domain event ready for Phase 5 to consume.
